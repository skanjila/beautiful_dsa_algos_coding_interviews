# How To Use This Repo Effectively

This repo can help a lot, but only if you use it as a training system rather
than as a pile of files to skim.

The goal is not to read everything.

The goal is to build:

- pattern recognition
- calm implementation habits
- reliable interview communication
- steady weekly progress without burnout

## The Right Mental Model

Use the repo in layers:

1. Pattern recognition
   Read `DEEP_DIVE.md` files and learn when to use each approach.
2. Code understanding
   Read the implementation and comments until you can explain the invariant.
3. Active recall
   Re-implement from memory without looking.
4. Verification
   Run the tests and compare your version to the repo version.
5. Interview rehearsal
   Explain the solution out loud in a simple, structured way.

If you only read the final code, you will feel productive without actually
building interview skill.

## The Best Daily Workflow

A good day of prep does not need to be long.

A strong default session is:

1. Pick one section.
2. Read one deep-dive entry.
3. Solve one problem from memory.
4. Run one test file.
5. Write down one thing you learned and one mistake you made.

That is enough for a useful day.

## A Good 60 To 90 Minute Session

### First 10 to 15 minutes

- open the relevant `DEEP_DIVE.md`
- review the recognition cues
- remind yourself what pattern you are practicing

### Next 20 to 30 minutes

- solve one main problem without looking
- if stuck, write the invariant before writing more code

### Next 10 to 15 minutes

- compare with the repo implementation
- read the comments and Big O explanation carefully

### Final 10 to 15 minutes

- run the tests
- log mistakes
- stop before the session turns sloppy

## How To Make Progress Every Day

Daily progress does not require solving a new hard problem every day.

Progress can be:

- understanding one pattern more clearly
- solving a medium problem faster
- reducing one repeated mistake
- explaining one solution more cleanly
- strengthening one weak area like graphs or system design

The real signal is consistency, not hero sessions.

## How To Avoid Burnout

Burnout usually comes from one of these mistakes:

- trying to study every section every day
- measuring progress only by number of problems solved
- doing only hard problems
- not reviewing mistakes
- staying in the repo too long after focus is gone

To avoid that:

- use one main section per session
- rotate difficulty
- keep one rest or light-review day each week
- stop when the quality of thinking drops
- prefer steady repetition over marathon sessions

## A Sustainable Weekly Rhythm

Example weekly rhythm:

- Day 1: core DSA pattern
- Day 2: another DSA pattern
- Day 3: trees / graphs / recursion
- Day 4: system design or ML/system-design prep
- Day 5: data science or data engineering
- Day 6: mock interview style mixed session
- Day 7: light review or rest

This keeps momentum without turning every day into the same type of stress.

## What To Do When You Feel Stuck

If you cannot solve a problem:

1. identify the pattern family
2. state the invariant
3. solve a smaller version
4. compare with the repo
5. come back to the same problem later

Do not confuse "I needed a hint" with "I am failing."

The wrong response is to abandon the section and jump to something easier every
time.

## How To Use The Repo For Different Interview Goals

### For software-heavy interviews

Focus on:

- DSA directories
- tests
- `DEEP_DIVE.md` guides

### For system design interviews

Focus on:

- `system_design/`
- `docs/service_design.md`
- `docs/study_guide_roadmap.md`

### For data or ML interviews

Focus on:

- `data_engineering/`
- `data_science/`
- `machine_learning_engineering/`

### For applied ML / MLE interviews

Focus on:

- ranking and retrieval topics
- feature engineering
- monitoring and drift
- ML system design
- coding consistency, not just ML theory

## How To Review Mistakes

Keep a short running list with only:

- problem name
- pattern
- mistake made
- correct insight

Examples:

- `word_ladder`: forgot BFS level meaning
- `three_sum`: forgot duplicate skipping
- `is_valid_bst`: used local child comparison instead of ancestor bounds
- `coin_change`: defined state correctly but wrong transition

This matters more than a giant notebook of copied solutions.

## How To Know You Are Improving

You are improving if:

- you recognize patterns earlier
- you write less random code
- you recover faster when stuck
- your explanations get shorter and clearer
- your mistakes repeat less often

That is better evidence than simply counting solved problems.

## Good Rules For The Last Few Weeks Before Interviews

- revisit solved mediums
- focus on communication and consistency
- do not constantly add brand-new topics
- practice explaining tradeoffs out loud
- keep sleep and pacing stable

At that stage, reliability matters more than novelty.
